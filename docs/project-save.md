## 2. プロジェクトの目的

### 長期的な目的

個人の認知能力を診断・格付けするツールではなく、複数の課題に対する操作過程を記録し、
個人の認知スタイルを探索するローカル研究プラットフォームを目指す。

主な観察対象は次のとおり。

- 正確性と速度のバランス
- 課題に取り組む順序
- 試行錯誤と修正
- 戦略の継続と切り替え
- 難易度や表現形式による変化
- 同一人物のセッション間・時系列変化
- 異なる課題に共通して現れる行動傾向

「認知スタイル」は固定的な人物類型として扱わない。生の行動ログから再分析可能な
観察傾向として扱う。

### 現在の具体的な目的

研究プラットフォーム全体を先に構築するのではなく、独立した最小実験として
「構造写像実験パック v0.1」を動かす。

この実験パックでは、表面的特徴が異なる対象間で関係構造を見つけ、対応付け、
再構成する過程を観察する。

優先順位は次のとおり。

1. ローカルで動く
2. 実際に触って遊べる
3. 生ログが保存される
4. 3課題を共通形式で比較できる
5. 後から分析方法を変更できる

## 4. 再設計の経緯

### 第1段階: 認知スタイル探索プラットフォームとして再定義

プロジェクトを次の観察基盤として再定義した。

```text
参加者
  └─ セッション
      └─ 課題ブロック
          └─ 試行
              └─ 行動イベント
```

重視する観点:

- 複数課題
- 行動戦略の観察
- 経時変化
- 認知スタイル探索

分析結果ではなく、生イベントを一次データとして保存する設計を採用した。

### 第2段階: 長期アーキテクチャの検討

当初はReact、FastAPI、PostgreSQL、分析パイプラインなども候補に挙げたが、
ユーザーの個人研究用途と運用方針を踏まえて簡略化した。

ユーザーが明示した優先事項:

- シンプルさ
- ローカル実行
- 学習コストの低さ
- メンテナンス性
- すぐ認知課題を試せること
- 依存を可能な限り減らすこと

避ける方針:

- PostgreSQL
- Docker
- Kubernetes
- 分散処理
- クラウド前提
- マイクロサービス

### 第3段階: 構造写像能力への焦点

構造写像を次の過程として定義した。

```text
構造の発見
  → 要素の対応付け
  → 規則の転用
  → 対応の修正
  → 説明・確信度
```

候補課題から次の3つを選定した。

1. 関係対応課題
2. 表面類似性対構造類似性課題
3. 構造再構成課題

この3課題を共通基盤で比較できる最小パックとして実装する方針になった。

## 5. 現在採用している設計思想

### 基本原則

- 診断ではなく探索
- 能力値より行動過程を重視
- 自動ラベルを急いで導入しない
- 生ログと派生指標を分離
- 課題間で同じセッション・試行・イベント形式を使う
- 分析方法を後から差し替え可能にする
- 外部依存を最小化する
- 一人で内容を理解し、運用できる構成にする

### データ階層

```text
session
  └─ trial
      └─ event[]
```

#### Session

- セッションID
- 参加者ID
- 開始・終了時刻
- アプリバージョン

#### Trial

- 試行ID
- セッションID
- 課題種別
- セッション内の順序
- 開始・終了時刻
- 所要時間
- 確信度
- 実際に提示した刺激
- 最終回答
- 暫定的な派生指標

#### Event

- 試行ID
- イベント順序
- 試行開始からの経過時間
- イベント種別
- 課題固有payload

### 解釈方針

現時点の`score`は、各課題で事前定義した構造との一致率であり、
認知能力スコアではない。結果画面にも診断ではないことを表示している。

## 8. 構造写像実験パック v0.1 の設計

### 共通インターフェース

JavaScript上で各課題クラスは概ね次の契約を持つ。

```text
constructor(trial, log)
render(root, onChange)
isComplete()
result()
stimulus()
```

- `render`: 共通画面内に課題を描画する
- `onChange`: 回答が完了可能な状態かを実験ランナーへ通知する
- `isComplete`: 必須回答が揃ったかを返す
- `result`: 最終回答と暫定指標を返す
- `stimulus`: 正答情報を除いた実提示条件を返す
- `log`: 共通イベント形式で操作を記録する

共通実験ランナー`ExperimentRunner`が次を担当する。

- セッション作成
- 課題順序のランダム化
- 試行開始
- 共通進捗表示
- 確信度収集
- 試行保存
- 次試行への遷移
- セッション完了
- 結果表示
- JSONダウンロード

### 課題1: 関係対応

左右に3要素と関係説明を表示し、同じ役割の要素を一対一対応させる。

実装済み問題:

- 研究チーム ↔ 料理店
- 河川 ↔ 情報システム

主なイベント:

- `source_selected`
- `mapping_set`
- `mapping_removed`
- `trial_presented`
- `trial_submitted`

保存する回答:

```json
{
  "mapping": {
    "source_id": "target_id"
  }
}
```

暫定指標:

- `score`
- `correct_mappings`
- `total_mappings`

### 課題2: 表面類似性対構造類似性

基準例と3候補を表示し、最も近い関係構造を持つ候補を選択する。

候補には次の性質を持たせている。

- 表面的には類似するが構造が異なる
- 表面は異なるが構造が一致する
- その他の妨害候補

実装済み問題:

- 図形・包含・作用関係
- 学校 ↔ 探査システム

主なイベント:

- `choice_selected`
- `choice_changed`

暫定指標:

- `score`
- `selected_structural`
- `selected_surface`

### 課題3: 構造再構成

バラバラの3要素を、参照構造で定義した3つの役割へ配置する。

実装済み問題:

- アプリ → 通知サービス → 利用者
- 制御装置 → 作業ロボット → 製品

主なイベント:

- `item_selected`
- `item_placed`
- `placement_removed`

暫定指標:

- `score`
- `correct_placements`
- `total_placements`

### 共通イベント

- `trial_presented`
- `trial_submitted`
- `confidence_changed`
- `focus_left`
- `focus_returned`

### 試行順序

- 3課題ブロックの順序をランダム化
- 各課題内の2問題もランダム化
- 合計6試行

同一課題の2試行は連続する。完全な試行単位ランダム化ではない。

## 13. 重要な設計判断と理由

### Python標準ライブラリだけを使う

理由:

- インストールなしですぐ動く
- 数年後にも復旧しやすい
- 個人研究でWebフレームワークを保守する必要がない
- 現段階のAPI規模では`http.server`で十分

代償:

- ルーティングや入力検証は手作業
- 規模が拡大した場合はフレームワーク移行が必要

今は妥当。APIや画面が大幅に増えるまで移行しない。

### SQLiteを使う

理由:

- Python標準
- 単一ファイル
- セッション・試行・イベントの関連を保てる
- JSONファイルを大量に管理するより検索・比較しやすい
- 将来Pandas等へエクスポート可能

### Vanilla JavaScriptを使う

理由:

- 3課題のUIには十分
- ビルド工程が不要
- npm依存がない
- 研究者として課題内容へ集中できる

### 課題問題は現時点でJavaScriptへ直書き

理由:

- v0.1を最短で遊べる状態にする
- 問題定義スキーマを早期に固定しない

次に問題数を増やす段階で、JSONまたは独立モジュールへ分離する。

### 生イベントを保存する

理由:

- 派生指標は後から変更できる
- 保存していない行動過程は復元できない
- 構造写像では最終正答より修正・形成順序が重要

### 課題結果を`score`で共通化する

理由:

- v0.1結果画面で課題間を最低限比較するため

注意:

- `score`は能力値ではなく、事前定義した対応との一致率
- 今後、課題固有指標を主表示にし、総合平均は安易に作らない

### 正解をブラウザ側に保持する

現状、各試行の`answer`はJavaScript内にある。これはローカル自己実験で
実装を簡潔にするための判断。

ただし`stimulus()`では`answer`を除外してDBへ保存している。

将来、他者を対象に実験する場合や改ざん耐性が必要な場合は、
正解判定をサーバー側へ移す。

確認後、次を記録する。

- 操作上わかりにくい点
- 問題文の曖昧性
- 対応変更のしやすさ
- 結果画面の有用性
- JSONログで不足している情報

これは今すぐ行うべき。分析機能より優先する。

### 優先度2: v0.1の不具合修正

手動テストで見つかった操作・保存バグだけを修正する。
この段階で大規模リファクタリングしない。

### 優先度3: 問題IDとバージョンの導入

各問題に次を追加する。

```json
{
  "task_version": "0.1",
  "problem_id": "relation-team-restaurant-001",
  "problem_version": 1
}
```

セッション比較を始める前に必要。

### 優先度4: 基礎的な行動指標

イベントログから次を計算する。

- 初回操作までの時間
- 最初の写像完成までの時間
- 対応変更回数
- 解除回数
- 最終提出前の修正時間
- 表面候補から構造候補への変更
- 誤配置から正配置への改善量
- フォーカス離脱回数

複雑なモデルではなく、決定論的集計から始める。

### 優先度5: セッション履歴と比較

- セッション一覧
- 同じ参加者IDの過去セッション表示
- 課題別の時間・一致率・修正回数比較
- JSONに加えてCSV出力

個人内変化の観察を始める最小機能。

### 優先度6: 問題数と難易度の拡充

各課題に複数の難易度を導入する。

- 要素数
- 関係数
- 階層深度
- 表面類似性の強さ
- 妨害候補数
- 部分一致
- 曖昧な複数写像

問題数を増やす前に、問題定義を外部JSONへ分離する。

### 後段階

- 戦略推定
- セッション内状態変化
- クラスタリング
- 長期個人内変化

十分なセッション数が得られてから導入する。

## 15. 新しいAIエージェント向け引き継ぎ情報

### 最初に行うこと

1. 本書を読む
2. `git status --short`を確認

4. `README.md`を読む
5. 次のテストを実行する

```powershell
python -m unittest discover -s tests -v
node --check static\app.js
git diff --check
```

6. ユーザーが実際に試したフィードバックを確認する

### 変更時の原則

- 日本語で簡潔に報告する
- 変更内容だけを説明する
- Dockerや外部サービスを勝手に導入しない
- 外部依存追加には明確な利益が必要
- 課題を増やすより、まずログ品質を改善する
- 診断表現や人物類型を追加しない
- 生ログを削らない
- DBスキーマ変更時は既存データ移行を考慮する
- 旧コードを復活させない
- `Dockerfile`削除は作業開始前からの状態であることを覚えておく

### コードの主要箇所

- `app.py`
  - `Storage`: DB初期化、保存、エクスポート
  - `AppHandler`: APIと静的ファイル配信
  - `main`: ローカルサーバー起動
- `static/app.js`
  - 試行データ定義
  - `BaseTask`
  - `RelationMappingTask`
  - `StructuralChoiceTask`
  - `ReconstructionTask`
  - `ExperimentRunner`
- `static/index.html`
  - 開始、実験、結果の3画面
- `static/style.css`
  - 共通UI
- `tests/test_app.py`
  - StorageとHTTP APIのテスト

### 注意すべき実装詳細

- SQLite接続は`Storage.connection()`で必ず閉じる。Windowsでは未クローズDBを
  テスト後に削除できない。
- 試行切替時は`#task-root`要素をcloneして置換している。これは前試行の
  イベントリスナーが残ることを防ぐため。
- 課題クラスの`stimulus()`は`answer`を削除して保存する。
- 完了ボタンは`isComplete()`が真になるまで無効。
- `performance.now()`は試行内経過時間、`Date.now()`は永続化用時刻に使用。
- 同一課題の問題データは現在`static/app.js`内にある。

### 現時点の完成条件

v0.1の完成条件は次のとおり。

- 3課題×2試行をブラウザで完走できる
- 各試行の操作イベントがSQLiteへ保存される
- 結果画面が表示される
- JSONログをダウンロードできる
- 自動テストが成功する

コード上は達成しているが、実ブラウザでの人手による完走確認が最後に残っている。
